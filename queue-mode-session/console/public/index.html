All containers are running. Unfortunately, so is the incident.

A self-paced n8n queue-mode lab for support engineers.

Where did this execution stop progressing, and what proves it?

The lab is a queue-mode deployment on your own machine: n8n main, two workers, Redis, Postgres and a small downstream API. You'll work three incidents in which every container stays up and healthy, and find out which process stopped doing its part.

Do the lessons in order; incident 3 is optional. It takes about two hours. Your answers to the prompts stay in this browser, and the Notebook page downloads them for the follow-up.

Trace one order through the deployment

About 20 minutes. Nothing is broken yet.

Follow one order from the webhook to the downstream API, and note which process told you each thing.

ServiceWhat it doesWhere its evidence is
n8n-mainServes the editor and receives webhooks. In queue mode it creates the execution record and puts a job on the queue, which makes it the producer. With manual offloading off, as in this lab, it also runs manual tests itself.docker compose logs n8n-main
redisHolds the Bull queue (the bull:jobs:* keys in one logical database) and carries pub/sub messages between main and the workers.docker compose exec redis redis-cli
n8n-worker (2)The consumers. Each one takes jobs off the queue and runs as many executions at once as its concurrency allows.docker compose logs n8n-worker
postgresWorkflows, encrypted credentials, and every execution record with its status and timestamps. Main and the workers both read and write it.the execution_entity table
fulfilment-apiThe downstream service the workflow calls. It works on 10 requests at once and answers the 11th with HTTP 429.docker compose logs fulfilment-api

The workflow, Order intake, has two triggers: a webhook for the shop and a manual trigger for the editor's Execute button. Both feed one HTTP Request node, which authenticates to the fulfilment API with a stored credential and makes up to three attempts, a second apart.

High priority, set by the customer. Self-hosted Enterprise, queue mode on Docker Compose.

It sends a new production order and a manual test, so moving the problem to main fails it.

Recorded evidence from a rehearsal run
Show the cause and the fix

Cause

The worker rebuild regenerated env/worker.env from a template, and the template came with a fresh N8N_ENCRYPTION_KEY. Main kept the original key, which is the one the Fulfilment API key credential was encrypted with.

  • Manual tests run on main, because offloading is off, and main can decrypt the credential. All seventeen tests passed without touching a worker.
  • Shop orders run on the workers, which can't decrypt it: 
    Credentials could not be decrypted. The likely reason is that a different "encryptionKey" was used to encrypt the data.
    The HTTP node tries three times, then the execution fails. No production request reaches the fulfilment API.
  • Every container reports healthy because a worker's readiness check covers its Postgres and Redis connections, and decryption isn't part of it.
  • In ./tools/evidence.sh config, the key hash on n8n-main-1 differs from the one on every worker.

Fix

Put main's key into env/worker.env and recreate the workers with docker compose up -d n8n-worker.

The tempting wrong fix

Copying the workers' new key into main. n8n saved the original key in main's volume on first boot, so main refuses to start:

The workers have no volume and no saved key to compare against, which is why they started with the wrong one without complaint.

Retest

Repeating the manual test doesn't check this fix, because the manual test never touched the workers. Send a production order and watch it succeed. The four failed shop orders are still error executions; now that the workers can decrypt again, Retry in the Executions list runs them successfully.

Setting OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=true makes manual tests run on the workers, so they take the same path as production.

./reset.sh

Incident 2: "Redis returned PONG"

About 30 minutes.

Urgent. Self-hosted Enterprise, queue mode on Docker Compose.

Since this afternoon no workflow executions finish. They appear in the list and never complete. The shop gets HTTP 200 back from the webhook, so n8n is receiving the orders.

We can connect to Redis from every container. We ran redis-cli ping in the Redis container and got PONG, and the worker health checks are all green.

Follow-up: Redis returned PONG, so we have ruled out Redis. Is this the Bull bug from the forum?

It passes when a new order completes and each of the five orders succeeded or was retried successfully.

Recorded evidence from a rehearsal run
Show the cause, both recoveries, and what happened to the five orders

Cause

CHG-4471 set QUEUE_BULL_REDIS_DB=1 in env/main.env and nowhere else. Main enqueues into database 1 and the workers wait on database 0. They share the server, port and password, and read different queues.

  • INFO keyspace shows keys in both db0 and db1. LLEN bull:jobs:wait is 5 in db1 and 0 in db0.
  • CLIENT LIST shows every worker's brpoplpush connection on db=0.
  • The executions stay new in Postgres, with no startedAt. Main logs Enqueued execution N (job 1): job numbering restarted at 1, because db1 holds a brand-new queue.
  • Health checks stay green. A worker's readiness check confirms it can reach Redis and doesn't look at which queue it reads.
  • Pub/sub keeps working too. Redis pub/sub ignores the logical database, and n8n names its channels from N8N_REDIS_KEY_PREFIX (n8n:n8n.commands and the others), which the queue settings never change. So main and the workers still exchange messages while no jobs move.

Recovery A: move the workers to database 1

This matches what the customer wanted. Set QUEUE_BULL_REDIS_DB=1 in env/worker.env and run docker compose up -d n8n-worker. The five jobs are still waiting in db1, so the workers pick them up within seconds and they succeed. Their queue wait equals the length of the outage.

Recovery B: move main back to database 0

New work flows again, and the five jobs stay in db1 with nothing reading them. When main restarts, it runs a queue recovery check: it looks for executions that are new in Postgres but have no job in its own queue, and marks them crashed. The same check runs every N8N_EXECUTIONS_QUEUE_RECOVERY_INTERVAL minutes, 180 by default.

You can still recover the orders. Retry on each crashed execution runs it again with its original webhook payload, and in the rehearsal the fulfilment API received the original order references.

Which recovery is right

The one that matches what the customer meant to do. They wanted DB 1, so recovery A. Recovery B leaves five orphaned jobs in db1. They're harmless; if someone wants them gone, delete those keys rather than running FLUSHDB on a Redis the billing app shares.

Incident 3: "We added workers. The queue got worse."

Optional. About 25 minutes.

High priority. Self-hosted Enterprise, queue mode on Docker Compose.

Black Friday is in three weeks, so we load-tested. Orders were failing, so we scaled workers from 2 to 5 and increased concurrency to 200. The dashboard says jobs are picked up faster than ever, but more orders fail than before.

Follow-up: We increased concurrency to 200. The errors are now significantly faster.

Recent changes: --concurrency=200 on the worker command, WORKER_REPLICAS=5, and "a clean-up of the worker env file". Proposed next step: 10 workers.

Recorded evidence from a rehearsal run
Show the precedence rule, the numbers, and a fix that fits the constraint

Which concurrency setting wins

On n8n 2.33.0, a worker uses N8N_CONCURRENCY_PRODUCTION_LIMIT whenever it's set to anything other than -1, and falls back to the --concurrency flag (default 10) otherwise. The "clean-up" copied N8N_CONCURRENCY_PRODUCTION_LIMIT=20 into env/worker.env, so every worker ignores --concurrency=200 and logs Concurrency: 20. The customer's 200 never took effect, and the real total was 5 × 20 = 100 execution slots.

The constraint

The fulfilment API works on 10 requests at a time and answers the 11th with HTTP 429. With 100 slots, most calls get refused. The HTTP node tries each call up to three times, a second apart, so executions take longer and more of them fail. Queue wait did get shorter, because work leaves the queue faster, and queue wait was the number on the customer's dashboard.

Fix

Fit the total number of slots to what the downstream can take. In the rehearsal, five workers with N8N_CONCURRENCY_PRODUCTION_LIMIT=2 (5 × 2 = 10) completed all 100 orders with no 429s. Each worker then warns that concurrency below 5 "can lead to an unstable environment", which is a good argument for fewer workers with more slots each. Going back to two workers at concurrency 5 works too. Longer term, ask the downstream owner for their real limit, and add rate limiting or batching instead of workers.

Applying a change

These change the lab, so there's no output here. Run them when a lesson calls for it.

docker compose up -d n8n-worker

Recreates the worker containers if their configuration changed since they were created, and leaves them alone if it didn't. Use it after editing env/worker.env or compose.yaml.

docker compose restart n8n-worker

Stops and starts the same containers. They keep the environment they were created with, so a restart doesn't pick up edits to env files or compose.yaml.

docker compose up -d --scale n8n-worker=3

Runs three worker replicas. The lab normally sets the count with WORKER_REPLICAS in .env, and ./reset.sh puts it back to two.

Not evidence on its own

  • Every container running and healthy. For n8n, readiness only means it can reach its database and Redis.
  • redis-cli ping returning PONG.
  • A successful manual execution while OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS isn't true. It ran on main.
  • A webhook answering 200 in "respond immediately" mode.
  • A worker count, a concurrency value in a file, or an empty queue.

Common problems

What you seeWhat to do
Docker is not runningStart Docker Desktop and wait until it reports running. docker info confirms it.
port is already allocatedSomething else holds 5690, 5691 or 5692, and lsof -i :5690 finds it. To move the lab, change MAIN_PORT, CONSOLE_PORT or FULFILMENT_PORT in both .env and env/baseline/lab.env.
Setup sits at "Starting n8n-main"The first boot runs database migrations and takes a minute or two; docker compose logs -f n8n-main shows progress. If main keeps restarting, give Docker more memory.
A worker is unhealthy or restartingRead docker compose logs --tail=40 n8n-worker, then run ./reset.sh.
Editor login failsUse owner@example.com and DockerLab2026 at http://localhost:5690. An IP address instead of localhost can make the browser drop the session cookie.
verify.sh says "no record of the incident's orders"Run that incident's setup.sh first. A reset clears the record.
The live panel says "not connected"Open localhost:5691, the copy your lab serves. A hosted copy of this page can only read your machine if your browser allows it, and some browsers don't.
Nothing makes sense any more./reset.sh --full puts everything back in a couple of minutes.
